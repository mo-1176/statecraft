# 0003. 禁止を積まず、構造で閉じる

- 状態: 採用（下書き）
- 日付: （記入）

## 決めたこと

やってほしくないことは、プロンプトで「〜しないでください」と頼むのではなく、**そもそもできない構造にする**。

構造で閉じきれない**形式の誤り**だけを、失敗した行に限って差し戻す。**答えの中身の良し悪しで作り直させる仕組みは、本体に持たない。**

一言でいえば、**事後に叱らない、事前に閉じる**。

## 困っていたこと

作者の言葉では、こうなる。

> 「やらないでください」では絶対に確実とは言えない。99%に漸近するのであれば、最初から100%にしてあげる。

ほかにも、次のことが起きていた。

- **出力を検査して差し戻し、作り直させるやり方は、生成の回数を増やすだけ。** しかも確実ではない。差し戻しの理由に「何なら通るか」を書くと、その形に合わせて値を作られる。
- **失敗のたびに禁止を足すと、規則どうしが綱引きを始める。** 実際に、軽いモデルの早すぎる停止に合わせた「調べ続けろ」と、強いモデルの止まらなさに合わせた「止めろ」が同じプロンプトに同居した。同じ文面で、あるモデルは止まりすぎ、別のモデルは止まらなかった（`prompts.py` の `POURING` の上のコメント）。

## どうしたか

### 構造で閉じているもの

| 起きてほしくないこと | 閉じ方 |
|---|---|
| 存在しない記憶のフィールドへ書く | 差分のスキーマの `field` を enum にする。enum はフィールドの定義から自動で作る |
| システムが書くフィールド（`requests` など）を書き換える | enum に出さない。書かれても差し戻さずに捨てる（直せないので、再生成のトークンを使わせない） |
| 記憶を消して、判断の履歴を失う | 消す経路を作らない。同じ id での差し替えだけ |
| 定義していない操作のキー（`remove` など）を捏造する | 差分のルートを配列にする。オブジェクトにすると、キーを置く場所が生まれる |
| 頼まれていないツールを呼ぶ | `FUNCTION_CALL` では `tasks` の対象しか API へ渡さない |
| 同じ呼び出しを繰り返す | 直前のステップで成功した呼び出しと同じものは、実行せずに拒否する |
| 空の条件で検索する | 必須の引数が空なら、実行しない |
| 際限なく調べ続ける | `max_steps` で打ち切る。停滞は検出して打ち切る |
| 判定できなかった実行が通る | `before_execute` は、型の違う値や例外を「許可」に倒さない |
| 審査役が、攻撃を含んだ記憶に影響される | 審査役・監査役を、監視される Network に入れない |
| 決まった手順を飛ばす | 毎回必ず要る手順は `initial_tools` に置き、LLM に選ばせない |

### 差し戻すもの（形式の誤りだけ）

- 差分の行が不正（存在しないフィールド、`status` の誤り、空の id）
- 実行したタスクの `status` が `next` のまま放置されている

差し戻す時は、**失敗した行だけ**を、**実行結果を渡さずに**出し直させる。回数は `max_memory_retries` まで。使い切っても止めず、通った分だけで進み、残った分は次のステップで1回だけ伝える。

### 本体が持たないもの

- **答えの中身の監査。** 記憶の更新の監査（`before_memory_diff`）は、利用側が選んで登録する仕組みで、何回で通すかも利用側が決める。組み込みの監査役（Network の `enable_auditor`）も、使うかどうかは利用側が選ぶ。
- **プロンプトでの禁止の積み増し。** 守らせたいことは、できるだけスキーマと構造で担保する。

## 引き換えに失うもの

- **柔軟さが減る。** 例えば、`target_names` に書いた対象以外は、その場の判断で呼べない。呼びたくなったら、記憶の更新でタスクを立て直す必要がある。
- **変えるコストが高い。** 規則の追加ではなく構造の変更になるので、本体（`src/statecraft/`）の変更になる。
- **形式の差し戻しは残っている。** フラットな行の配列にしたため、`tasks` の行だけ `status` を必須にする、といったことはスキーマで表せない。そこは受け取り側の検査に頼っている。
