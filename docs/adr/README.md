# 設計判断の記録（ADR）

ADR（Architecture Decision Record）は、設計で決めたことを1件1ファイルで残す記録です。コードは「何をしているか」を語りますが、「なぜ他のやり方にしなかったか」は語りません。直す人が理由を知らずに思想を壊さないように、ここへ残します。

## 書き方

- ファイル名は `番号-短い名前.md`（例: `0004-xxx.md`）。番号は通しで振ります。
- 決定を覆した時は、元のファイルを消さずに「状態」を `0007 で置き換え` のように書き換え、新しい ADR を足します。
- 長さは1〜2画面に収めます。細部はコードのコメントか concepts の文書へ。

```markdown
# 番号. 決めたこと（1行）

- 状態: 採用 / 置き換え（→ 番号） / 廃止
- 日付: YYYY-MM-DD

## 決めたこと
何をどうしたか。

## 困っていたこと
これをしないと、具体的に何が起きるか。実際に起きた失敗の例があれば書く。

## どうしたか
仕組みとしてどう解決したか。

## 引き換えに失うもの
この設計で諦めたこと。後から「ここ不便だから直そう」と思った人が、
それが意図された不便だと分かるように書く。

## 関連
関係するコード・文書・ADR。
```

## ADR の候補

`src/statecraft/prompts.py` と `memory.py` のコメントには、「こういう失敗が実測されたので、この文を足した／この形にした」という履歴が多く残っています。そのうち、プロンプトの文言を超えて構造に効いている判断は、ADR へ移す候補です。

- 差分のルートを配列にした（オブジェクトだと、定義していないキーを捏造する）
- 問いの置き場を `questions_to_research`（調べる）と `questions_to_ask`（尋ねる）に分けた
- 利用者の原文を `conversation` として全員に読ませる形へ変えた
- ツールの無効化を、どの phase でも止めている
