# 0002. ループを自前で持ち、ツールの説明を載せる時を分ける

- 状態: 採用（下書き）
- 日付: （記入）

## 決めたこと

ツールを呼ぶ生成には、API の function calling を使う。ただし、**呼び出しの往復**（結果を会話として返し、そのまま次の生成を続ける形）には任せない。

- **何を提示するか**は、記憶の `tasks` の `target_names` で決まる。
- **結果をどこで見せるか**は、statecraft のループが決める（評価する1回の生成だけ）。

ツールの説明は `summary` / `usage` / `evaluation` の3つに分け、載せる時を変える。

## 困っていたこと

作者の言葉では、こうなる。

> ツールの戻り値に対する読み方のナレッジは、戻り値を見るタイミングでしか必要にならない。それを切り離せる実装にした。

API の往復に任せると、次のことが起きる。

- **ツールの説明は、定義として最初から全部渡すしかない。** いつ使うか、引数の注意、結果の読み方まで、1つの説明に入る。まだ結果を見ていない段階から、結果の読み方がプロンプトに載り続ける。
- **ツールが増えるほど入力が膨らみ、関係ない指示に引っ張られる。**
- **結果が会話に積もる。** 以降のすべての生成に、生のデータが載り続ける（[0001](0001-memory-centered-prompt.md) と同じ問題）。
- **結果の読み方を人格定義に書くと、ツールを足すたびに統括の側を書き換えることになる。**

## どうしたか

| 説明 | 載る時 |
|---|---|
| `summary` | 常時。一覧の1行として。親のエージェントからも見える |
| `usage` | そのツールを持つエージェントが計画する時（`INITIAL_MEMORY` / `MEMORY_UPDATE` の一覧）と、呼び出し候補として API へ渡す時（`FUNCTION_CALL`）。親からは見えない |
| `evaluation` | 結果が返った瞬間に、結果と一緒に1回だけ |
| 結果の本文 | 評価する `MEMORY_UPDATE` の1回だけ。以降は「※結果はmemoryへ要約済み」 |

`FUNCTION_CALL` では、`tasks` で `next` / `next_parallel` になっている対象だけを API へ渡し、`tool_choice="any"` で呼び出しを強制する。何を呼ぶかは記憶で決まっていて、この生成が決めるのは**引数だけ**になる。

## 引き換えに失うもの

- **プラットフォームから、ツールの呼び出しと結果の対応が見えにくい。** 結果は、次の生成のプロンプト（`【今回の実行結果】`）の文章として届く。プラットフォーム側の監視や安全対策（例: Azure の Foundry のガードレールの「ツールの応答」の検査、間接プロンプトインジェクションの判定）は、「これはツールの結果だ」という区別を使えない。
- **プロバイダが用意している、ツールの往復を前提にした機能**（サーバー側で動くツール、会話の保存など）とは、そのままでは噛み合わない。
- 思考の継承（`carry_thoughts`）を有効にした場合は、過去の呼び出し要求に「実行済み」かエラーだけを対にして送り返す。生の戻り値は会話に残さない（プロバイダが、結果の無い呼び出し要求を断るため）。
