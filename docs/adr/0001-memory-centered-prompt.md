# 0001. 記憶を中心に、毎回プロンプトを組み立て直す

- 状態: 採用（下書き）
- 日付: （記入）

## 決めたこと

生成を phase に分け、ステップをまたいで引き継ぐのは**記憶だけ**にする。毎回の生成は、記憶と、その生成に要るものだけからプロンプトを組み立て直す。

ツールの結果・初期記憶のためのナレッジ・結果の読み方・ツールが返した添付は、**それを評価する1回の生成にだけ**載せる。中身は記憶へ書き起こさせ、以降のステップには載せない。

## 困っていたこと

会話の履歴に、ツールの結果や指示文を積み続ける形だと、次のことが起きる。

- **入力トークンが、ステップごとに増え続ける。** ステップ数 × それまでの全量を、毎回払うことになる。
- **指示文が、毎回「外から来た命令」として読まれ続ける。** 一度しか要らない手順や、ツールの結果に紛れた文章も、プロンプトに残っている限り、モデルは毎ステップそれに反応する。関係ない場面で特定の指示に過剰に反応したり、途中から最初の目的を外れたりする（暴走）。
- **「今は関係ない指示だ」と判断できるかが、モデルの賢さ次第になる。** 軽いモデルほど崩れる。

作者の言葉では、こうなる。

> 入力トークンを最小限に抑え、ナレッジに含まれる指示文を自分の知識として吸収する。それ以降に命令文が出てこない形にすることで、暴走を防ぐ。モデルの賢さに頼らない設計。

## どうしたか

- **記憶を「自分の考え」として読ませる。** 共通の指示（`POURING.common`）で、記憶は「あなた自身の考えそのもの」だと伝える。共有の記憶は、他のエージェントが書いたものでも「自分がすでに知っていること」として読ませる（`memory.py` の `STANCE`）。
- **材料は1回だけ見せ、記憶へ書き起こさせる。** 結果を評価する生成（`MEMORY_UPDATE`）には「材料はこの生成が終わると消える。書き起こした分だけが残る」と伝える（`TRANSCRIPTION_RULES`）。以降の実行履歴では、結果の本文が「※結果はmemoryへ要約済み」に置き換わる。
- **常時載せるものを小さくする。** `knowledge` は全 phase に載るので、用語の辞書のように常に要るものだけにする。規程やルールは tool で取りに行かせ、読んだ時に記憶へ書き起こさせる。
- **変わらないものを前に、変わるものを後ろに置く。** 人格定義やナレッジは前に、記憶の中身と実行結果は後ろに置き、プロンプトキャッシュに乗りやすくする（→ [concepts/phases-and-prompts.md](../concepts/phases-and-prompts.md)）。

一言でいえば、指示を**命令として見せ続けるのではなく、理解として持たせる**。

## 引き換えに失うもの

- **書き起こさなかったものは消える。** 回答の質が、書き起こしの質に依存する。`TRANSCRIPTION_RULES` で「出力の量は惜しまない」「迷ったら書く」と伝えているのはこのため。
- **記憶を書く phase の分だけ、生成回数と出力トークンが増える。** 1〜2個の役割しか持たないエージェントには、記憶を持たない `ReflexAgent` を使う。
- **1回の生成の中で見えるものが限られる。** 前のステップの生の結果を見直すことはできない。取り直すには、もう一度実行する必要がある。

## よく来る反論への答え

- **「長い文脈を扱えるモデルなら、全部渡せばいい」**: 入るかどうかと、正しく優先できるかどうかは別の話。しかも入力の量 × ステップ数で費用が増える。
- **「RAG で拾えばいい」**: RAG が解決しているのは「何を入れるか」。この決定が扱っているのは「入れたものが、どう効くか」。拾ってきた断片も、毎回差し込めば、命令として見せ続ける問題はそのまま残る。
