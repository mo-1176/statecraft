# 設計の思想

statecraft は、複数の AI エージェントを1つのチームとして動かすための Python フレームワークです。この文書は、statecraft が何を大事にしているかをまとめたものです。ほかの文書に書いてある仕組みは、どれもここから導かれています。

---

## 1. 記憶が、思考そのものである

statecraft のエージェントは、1回の応答の中で何度も生成を行います（調べる前に見立てを立てる、ツールを呼ぶ、結果を読む、答える）。**それぞれの生成は別々の呼び出しで、生成をまたいで引き継がれるのは記憶だけです。**

だから記憶は、ただのメモではありません。依頼をどう読んだか、今どう見ているか、何を判断したか、次に何をするか。エージェントの考えは、すべて記憶に書かれています。エージェントには、記憶を「あなた自身の考えそのもの」として読ませます。

共有の記憶（`SharedMemory`）は、全エージェントが同じ実体を読み書きするホワイトボードです。他のエージェントが書いたものも、報告書としてではなく「自分がすでに知っていること」として読ませます。エージェントは別々の人格ではなく、**1つの理解を共有する、1つの思考の延長**として扱います。

→ [memory.md](memory.md)

## 2. モデルの賢さに頼らない

1回の生成に任せる判断を、できるだけ狭くします。

- **phase で生成を分けます。** 見立てを立てる、引数を決める、結果を書き起こす、答える、をそれぞれ別の生成にします。
- **ツールを呼ぶ生成が決めるのは、引数だけです。** 何を呼ぶかは、記憶の `tasks` で前のステップがすでに決めています。
- **判断するのは、記憶を書くステップです。** 実行のステップは引数を決めるだけ、回答のステップは記憶に書かれた判断をもとに語るだけです。

考える範囲が狭いので、軽いモデルでも流れが崩れにくくなります。品質を上げたい所だけ、phase ごとに重いモデルを割り当てられます。

→ [phases-and-prompts.md](phases-and-prompts.md)

## 3. 命令として見せ続けず、理解として持たせる

ツールの結果、初期の記憶を作るためのナレッジ、結果の読み方は、**それを使う1回の生成にだけ**載せます。中身は記憶へ書き起こさせ、以降のステップには載せません。

作者の言葉では、こうなります。

> 入力トークンを最小限に抑え、ナレッジに含まれる指示文を自分の知識として吸収する。それ以降に命令文が出てこない形にすることで、暴走を防ぐ。

プロンプトに残り続ける指示文は、毎回「外から来た命令」として読まれます。モデルは、その命令に毎ステップ反応し続けます。一度読んで記憶に書いたものは、「自分の理解」になります。命令ではないので、今の場面に当たるかを、自分で考えて使います。

→ [ADR 0001](../adr/0001-memory-centered-prompt.md)、[ADR 0002](../adr/0002-own-tool-loop.md)、[knowledge.md](knowledge.md)

## 4. 禁止を積まず、構造で閉じる

やってほしくないことは、プロンプトで「〜しないでください」と頼むのではなく、そもそもできない構造にします。

> 「やらないでください」では絶対に確実とは言えない。99%に漸近するのであれば、最初から100%にしてあげる。

- 書けないフィールドは、差分のスキーマに現れません。
- 記憶を消す経路はありません。
- 頼まれていないツールは、提示されません。
- 判定できなかった実行は、通りません。

出力を検査して作り直させるやり方は、生成の回数を増やすだけで、しかも確実ではありません。**事後に叱らず、事前に閉じます。** 構造で閉じきれない形式の誤りだけを、失敗した行に限って差し戻します。

→ [ADR 0003](../adr/0003-close-by-structure.md)、[failure-handling.md](failure-handling.md)

## 5. ナレッジは参考であって、枷ではない

渡したナレッジや、ツール・エージェントの説明は、判断の参考です。エージェントの行動を縛るものではありません。

ナレッジに書かれた手順は、それが想定している場面のためのものです。今の依頼がその場面に当たるかをエージェント自身に見極めさせ、当たるなら従わせ、当たらないなら使わせません。正しいのは、ナレッジどおりに動くことではなく、依頼者の目的に届くことです。

この考えは、全エージェントの共通の指示（`POURING.common` の【進め方】）に入っています。

→ [knowledge.md](knowledge.md)

## 6. 失敗のたびに、規則を足さない

LLM が望まない動きをした時に、その場面専用の規則をプロンプトへ足していくと、規則どうしが綱引きを始めます。statecraft では実際に、軽いモデルに合わせた「調べ続けろ」と、強いモデルに合わせた「止めろ」が同居し、同じ文面で、あるモデルは止まりすぎ、別のモデルは止まらなくなりました。

そこで、プロンプトは**一般的な考え方で短く書き**、場面ごとの禁止は積みません。失敗の例は規則にせず、考えの方を言い直します。守らせたいことは、できるだけスキーマと構造で担保します。

どの失敗を見て、どの文を足したかは、`prompts.py` と `memory.py` のコメントに履歴として残しています。

## 7. 運用の方針は、フレームワークが持たない

何回で諦めるか、何秒待つか、どのモデルへ逃がすか、何回で監査を通すか、次のターンへ何を持ち越すか。これらは、使う場面によって正解が変わる**運用の方針**です。

statecraft はこれらを決めず、利用側が `Interceptor` や保存・復元のコードで決めます。フレームワークが持つのは、どの方針でも変わらない仕組み（記憶、ループ、配線、検証）だけです。

→ [reference/interceptor.md](../reference/interceptor.md)

## 8. PoC の延長線上に、エージェントはいない

細かい機能を実装して、要件の点を1つずつ埋めていくことは、誰にでもできます。PoC も、その形なら作りやすいです。「この聞き方には、この答え」が1つ通れば、動いているように見えるからです。

実務では、そうはいきません。

- 利用者がどんな聞き方をしてくるかは、前もって分かりません。
- 運用が進むほど、「この問いはどの機能の担当か」の境界があいまいになっていきます。
- 境界を判定するために、指示文が増えていきます。「この場合はこう、ただしこの場合は別」と、利用者の要求を細かく分類することになります。
- **無限通りの問いを、有限の分類で受け止めることは、実質的に不可能です。** 分類を足すほど、分類どうしの境目で新しい取りこぼしが生まれ、また指示文が増えます。

**if の無限のネストで、エージェントは作れません。** 指示文で分類を重ねる作り方は、プロンプトの中に「もし〜なら、ただし〜の場合は、さらに〜なら」という分岐を書き続けるのと同じです。

しかも、その作り方では、**機能を足すのが極端に難しくなります。**

- 新しい機能を1つ足すたびに、既存のすべての分岐との関係を考え直すことになります。「この問いは新しい機能の担当か、前からある機能の担当か」の境界が、足した分だけ増えるからです。
- 境界の指示を1つ直すと、別の分岐の判定が変わり、前は正しく答えていた問いが答えられなくなります（デグレ）。どこが壊れたかは、全部の聞き方を試すまで分かりません。
- 分岐どうしの組み合わせは、機能の数より速く増えます。ある所から先は、誰も全体を把握できなくなります。

だから statecraft は、**利用者の聞き方に、なるべく依存しない作り**を目指します。

- **問いを分類して担当へ振り分けるのではなく、問いを読んで、何が分かれば答えられるかを考えさせます。** goals・tasks・state_briefing は、どの聞き方の問いにも同じ形で使える、考えるための骨組みです。
- **プロンプトは、場面ごとの規則ではなく、一般的な考え方で書きます**（→ 6）。「この聞き方ならこう答える」を積むのではなく、「依頼者は何を、いつ決めようとしているか」を読ませます。
- **依頼を、ナレッジの手順や決まった型に無理に当てはめさせません**（→ 5）。
- **窓口は1つにし、知識は1か所に持ちます**（→ [network-placement.md](network-placement.md)）。利用者に「どのエージェントに聞くか」を選ばせると、その選び方自体が、新しい分類になります。

PoC に機能を足していっても、実務で動くエージェントには近づきません。実務で要るもの（聞き方に依存しない考え方の骨組み、知識の置き場、失敗の扱い、観測）は、最初に骨組みとして決めておかないと、後から足せないものばかりだからです。

## 引き換えにしているもの

この思想で作ったことで、諦めているものもあります。

| 諦めているもの | 理由 |
|---|---|
| 1回の応答の生成回数の少なさ | 記憶を書く phase がある分、生成が増える。単純な役割には、記憶を持たない `ReflexAgent` を使う |
| 出力トークンの少なさ | 結果は要約ではなく書き起こさせるので、出力が長くなる |
| 書き起こしに頼らない回答 | 書き起こさなかったものは、次のステップには存在しない |
| プラットフォームからの見えやすさ | ツールの結果は次の生成のプロンプトの文章として届くので、外の監視や安全対策からは「ツールの結果」と区別しにくい |
| その場の柔軟さ | 何を呼ぶかは記憶のタスクで決まるので、その場の思いつきでは呼べない |
