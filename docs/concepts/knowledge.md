# ナレッジと説明文の載せ方

エージェントに渡す文章は、何種類もあります。statecraft では、それぞれを**要る時にだけ**載せます。常に全部を載せると、入力トークンが増えるだけでなく、今は関係ない指示にモデルが引っ張られるためです（→ [ADR 0001](../adr/0001-memory-centered-prompt.md)）。

---

## いつ、どこに載るか

| 文章 | 載る時 | 置き場所 | 用途 |
|---|---|---|---|
| `system_instruction` | 全 phase | system_instruction（エージェントごとの段） | 人格・役割の定義 |
| `knowledge` | 全 phase・全ステップ | system_instruction（エージェントごとの段の先頭） | 常に要る前提（用語の辞書など） |
| `initial_knowledge` | `INITIAL_MEMORY` だけ | prompt 側（【この構築のためのナレッジ】） | タスクの立て方の例など |
| `answer_knowledge` | 最終回答の生成だけ（打ち切り・停滞の回答も含む） | prompt 側（【この回答のためのナレッジ】） | 答え方の方針 |
| tool / agent の `summary` | 常時 | 一覧・API の定義 | 何をするものか（1行） |
| tool / agent の `usage` | 持ち主が計画する時と、呼び出し候補として API へ渡す時 | 一覧（`INITIAL_MEMORY` / `MEMORY_UPDATE`）・API の定義（`FUNCTION_CALL`） | スキーマで表せない使い方 |
| tool / agent の `evaluation` | 結果が返った時に1回 | 結果のすぐ下（【この結果の解釈】） | 結果の読み方 |
| tool の結果の本文 | 評価する `MEMORY_UPDATE` の1回だけ | prompt 側（【今回の実行結果】） | 書き起こしの材料 |

- `initial_knowledge` と `answer_knowledge` は、常時のルールではなく、**その生成の材料**として prompt 側に載ります。記憶を作る phase を持たない `ReflexAgent` では、`initial_knowledge` は一度も載りません。ループの中で答える `ReflexAgent` では、`answer_knowledge` も載りません。
- `usage` は**使う本人にだけ**渡ります。そのエージェントへ依頼を送る親からは、`summary` の1行だけが見えます。親に要るのは「この子は何ができるか」で、「どう使うか」ではないためです。
- `ReflexAgent` は記憶へ書き起こさないので、tool の結果の本文は実行履歴に残り続けます。

## ナレッジは、参考であって枷ではない

全エージェントの共通の指示（`POURING.common` の【進め方】）には、次の考えが入っています。

> 渡されたナレッジや、使えるtool・エージェントの説明は、判断の参考であって、あなたの行動を縛る枷ではない。ナレッジに書かれた手順は、それが想定している場面のためのものである。今の依頼がその場面に当たるかを自分で見極め、当たるなら従い、当たらないなら使わない。

ナレッジを書く側は、**どの場面のための手順か**が読み取れるように書いてください。「セール情報を探す時は、まずこのページを開く」というナレッジが、特定の店のセールや無料配布の問いにまで当てはめられた、という失敗が実際にありました。

## 書き分けの指針

### knowledge は小さく保つ

`knowledge` は全 phase・全ステップに載るので、ループが回った分だけ入力トークンを払います。細かい規程やルールを書くと、プロンプトを汚します。常に要る前提（用語の辞書など）だけにしてください。

### 規程やルールは、tool で取りに行かせる

細かい規程は、tool で取りに行かせます。取ってきた結果は、評価する1回の生成で記憶へ書き起こされ、以降は「自分の理解」として残ります。**命令として見せ続けるのではなく、理解として持たせる**、という statecraft の考え方の中心がここです。

### 初期の記憶を作る時にしか読まないものは、initial_knowledge へ

タスクの立て方の例（few-shot）のように、初期の記憶を作る時にしか読まないものを `knowledge` に置くと、読まれない場所で払い続けることになります。

### 答え方の方針は、answer_knowledge へ

記憶には、確かめられなかったことや調べた経緯も残します。次の一手を決めるのに要るからです。一方、答えでそれを全部話すと、依頼者には要らない裏側の話が増えます。記憶に何を残すかと、答えで何を話すかを分けたい時に、答え方の方針を `answer_knowledge` に置きます。記憶を書く phase には載らないので、記憶の書き方には影響しません。

### 結果の読み方は、evaluation へ

各ツールの結果の見方を人格定義に書くと、ツールの数に比例してプロンプトが伸び、ツールを足すたびに統括の側を書き換えることになります。結果の読み方は、そのツールの `evaluation` に置いてください。

## 文書が多い場合

扱う文書が多く、`knowledge` に丸ごと入れられない場合も、文書を自動で検索してプロンプトに差し込む仕組みは、statecraft は持ちません。差し込まれた断片は、毎回プロンプトに載る外の文章になり、上の問題がそのまま残るためです。

代わりに、**検索を tool として持たせ、何を読むかをエージェントに決めさせます。** 例えば、次の2つを組にします。

- 検索の tool: 検索語を受けて、文書の ID・場所・短い抜粋を返す
- 読む tool: ID と範囲を受けて、元の文書の本文をまとまった単位で返す

抜粋は「どこを開くかの手がかり」としてだけ使い、判断の材料は開いた原文から取らせます。検索で出なかったことが「存在しない」ことにならないよう、検索の tool の `evaluation` に限界を書いておきます。
