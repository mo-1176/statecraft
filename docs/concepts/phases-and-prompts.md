# phase とプロンプトの組み立て

1回の応答の中で、エージェントは何度も生成を行います。1回の生成には必ず1つの **phase** が対応し、phase によって「プロンプトに何を載せるか」「ツールを渡すか」「どんな形で答えさせるか」が変わります。

定義は `src/statecraft/prompts.py`、組み立ては `src/statecraft/agent.py` の `_build_system_instruction` と `_build_prompt` にあります。

---

## phase の一覧

| phase | 何をするか | tool を API へ渡す | 出力の形 | 記憶の書き方 | 思考の方向づけ | 利用者の添付 |
|---|---|---|---|---|---|---|
| `INITIAL_MEMORY` | 依頼を読み、見立て・goals・最初の tasks を書く | — | 差分のスキーマ | ✅ | ✅ | ✅ |
| `FUNCTION_CALL` | tasks の対象を呼ぶ。決めるのは引数だけ | ✅（`"any"` で強制） | — | — | — | — |
| `MEMORY_UPDATE` | 結果を書き起こし、次の tasks か止める判断を書く | — | 差分のスキーマ | ✅ | ✅ | —（tool の添付は渡す） |
| `ANSWER` | 実行すべきタスクが無くなったので回答する | — | `output_schema` | — | — | ✅ |
| `CUTOFF_ANSWER` | `max_steps` を使い切ったので回答する | — | `output_schema` | — | — | ✅ |
| `STALLED_ANSWER` | 停滞を検出して打ち切ったので回答する | — | `output_schema` | — | — | ✅ |

- `ReflexAgent` は `INITIAL_MEMORY` と `MEMORY_UPDATE` を通りません。`FUNCTION_CALL` で全ツールを提示し（`"auto"`）、テキストが返った時点でそれが回答になります。
- 利用者の添付（画像や PDF）は、初期の記憶を作る時に書き起こさせ、ループの途中では渡しません。入力トークンがループの回数分かかるためです。最終回答では再び渡します。要約では必ず失われる文脈があり、回答の質に直接響くので、そこは節約しません。

phase ごとの組み立ての違いは、if 文ではなく `PhaseSpec` というデータで持っています。phase が増えても分岐が増えないようにするためです。

---

## 1回の生成の形

生成は、**変わらない部分（system_instruction）** と **毎回変わる部分（prompt）** に分けて組み立てます。

```
system_instruction（変わる頻度で3段に分ける）
  ① 記憶の構成が同じエージェントの全 phase で同じ
       【全ステップ共通の姿勢】          POURING.common
       【memoryの読み方】                各フィールドの description
  ② エージェントごと（phase が変わっても同じ）
       【ナレッジ】                      knowledge
       【あなたに適用された人格定義】    system_instruction
       【あなたが受け取る依頼の形】      input_schema の説明
       【あなたが返す最終回答の形】      output_schema（ReflexAgent だけ）
       【利用者から直接受けた依頼の扱い】 respond() で起動した時だけ
  ③ phase ごと
       【memoryの書き方】                how_to と書き分けの判断（記憶を書く phase だけ）
       【実行可能なtool / agent】        一覧（tool を API へ渡さない phase だけ）
       【思考の方向づけ】                POURING.thinking（記憶を書く phase だけ）
       【現在のステップでやるべきこと】  PHASE_SPECS の instruction

prompt（毎回変わる）
  【依頼内容】          委譲された時だけ（利用者からの依頼は conversation にある）
  【現在のmemory】
  【あなたの実行履歴】  Agent では、書き起こし済みの結果の本文は隠す
  【今回の実行結果】    結果を評価する phase だけ
  （phase ごとの追加）  停滞の検出 / 前回反映されなかった項目 / この構築のためのナレッジ /
                        出力例 / 監査の指摘 / この回答のためのナレッジ / 実行されていないタスク
  【残りの実行回数】    記憶を書く phase だけ
  【現在時刻】          必ず最後
```

### なぜこの順番か

プロバイダのプロンプトキャッシュは、**先頭から一致する部分**を再利用します。そのため、変わらないものほど前に、変わるものほど後ろに置いています。

- system_instruction の3段は、変わる頻度の順です。②と③が逆だと、phase が変わるたびにナレッジ全体が再送になります。
- Claude と GPT-5.6 以降の OpenAI は、区切りまでが丸ごと一致した時にしかキャッシュが当たりません。そのため、3段の境界にキャッシュの区切りを打ちます（区切りを受け付けないモデルは、断られた時点で覚えて、以降は区切り無しで送ります）。
- 現在時刻は、生成ごとに必ず変わる唯一の値なので、いちばん最後に置きます。前に置くと、後ろに続くものがキャッシュの一致範囲から外れます。秒まで出すのは、締め切りや営業時間のように、時刻で可否が変わる判断をさせるためです。
- 依頼内容はセッションの中では変わりませんが、ルールではなく「答えるべき対象」なので、system_instruction 側には置きません。

`section()` は見出しと本文を必ず組で扱い、本文が空なら見出しごと消します。中身の無い見出しの分まで、毎回トークンを払わないためです。

## 全 phase に流し込む文言 — POURING

### `POURING.common`

全エージェント・全 phase に載ります。中身は3つです。

1. **【あなたが動いている仕組み】** 複数のエージェントの中の1体であること。1回の応答がステップの繰り返しで進むこと。ステップをまたいで引き継がれるのは記憶だけで、実行の結果が見えるのは直後の記憶の更新だけであること。発話するのは、利用者から直接依頼を受けたエージェントだけであること。
2. **【進め方】** 依頼者の目的に責任を持つ担当者として考えること。処理はステップに分かれていても、思考は1本であること。ナレッジは参考であって枷ではないこと。そのうえで、1本の軸に沿った5つの進め方を示します。
   1. 何を答えるかを決める
   2. goals に答えるのに足りない所を調べる
   3. goals に答えられたら止める
   4. 受け取ったものは、見立てを通して読む
   5. 答えは、理解から語る
3. **【サブエージェントの扱い】** サブエージェントは tool とは違う担当であり、その回答は判断材料として自分の基準で評価すること。

phase で生成を分けると、各ステップが目の前の欄を埋める作業になりやすくなります。生成を分けたのはフレームワークの側なので、「思考は1本で、各ステップは同じ見立てを一手ずつ進める」とつなぎ直すのも、フレームワークの側が持ちます。

### `POURING.thinking`

記憶を書く phase にだけ載ります。**判断するのはこのステップである**ことを伝えます。実行のステップは引数を決めるだけで、回答のステップは記憶に書かれた判断をもとに語るだけです。目の前の材料で言えることは、ここで言い切って記憶へ書かせます。後のステップに送った判断は、誰にも下されないためです。

## 記憶を書く phase に足す文言

| 文言 | 中身 | 置き場所 |
|---|---|---|
| `TRANSCRIPTION_RULES` | 材料は、書き起こした分だけが残る。要約ではなく書き起こし。迷ったら書く | 記憶を書く phase の指示の中 |
| `COMPLETION_CRITERIA` | goals に答えられるなら止め、どの事実で答えるかを decisions へ書く。足りないなら tasks を立て、使う値を vars へ写しておく | 記憶を書く phase の指示の**最後** |
| `STALL_NOTICE` | 直前と全く同じ実行が繰り返されている。タスクを閉じるか、対象を変えるか、条件待ちに戻すか | 停滞を検出した時だけ |
| `DIFF_EXAMPLE` | 差分の出力例。1つの結果を複数の書き先へ展開し、問いに直接答えない条件や例外も残す形を見せる | 記憶を書く phase の prompt 側 |

`COMPLETION_CRITERIA` を最後に置いているのは、前の方に書いた条件ほど落とされやすいためです。

## プロンプトを直す時の約束

- **規則は1か所にだけ置きます。** phase をまたいで効く規則は記憶の `how_to` に、その phase でしか起きないことは `PHASE_SPECS` の instruction に置きます。
- **場面ごとの禁止を積みません。** 失敗の例は規則にせず、考えの方を短く言い直します（→ [philosophy.md の 6](philosophy.md#6-失敗のたびに規則を足さない)）。
- **どの失敗を見て、どの文を足したかを、コメントに残します。** `prompts.py` の `POURING` の上には、「GPT-6 Sol で実測された止まらなさの形と、それに当てた文」の一覧があります。後から文を消したくなった人が、その文が何を防いでいたかを知るためです。

## 思考の継承（carry_thoughts）

既定では、前の生成の思考が次の生成へ引き継がれます。プロバイダの思考は取り出して別の場所へ入れられないので、過去の生成を思考の署名ごと会話として送り返す形を取ります。

- 過去の発話は縮めて積みます。記憶の全体と実行履歴は今回の発話が最新のものを載せるので、過去の発話には残しません。
- ツールの生の戻り値は会話に残しません。呼び出し要求に対にするのは「実行済み」かエラーだけです。
- 対応しているのは `GeminiLLM` と `OpenAILLM`（とそれを継承する `AzureOpenAILLM`）です。

詳しくは README の「思考の継承」にあります。
